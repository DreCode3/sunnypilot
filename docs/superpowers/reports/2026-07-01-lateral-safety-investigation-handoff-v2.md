## 4. Current LEADING understanding
**The new build's lateral correction is weak and slow: it under-commands to hold the lane, and it is sluggish to recover after any perturbation (lane change, brief blindness, sun glare).** This single description accounts for every verified fact: the weak-correction event (§3.5), the recovery lag (§3.6), the lane-change prominence (§3.7), the worse centering (§3.8), and the overpass drift (§3.9, blowout = one trigger). It is a **model/inference-engine LATERAL-OUTPUT problem** — NOT the camera (blowout was a one-off), NOT the actuation/feed-forward (wheel follows command), NOT the panda safety layer.

## 5. TWO LIVE SUSPECTS (pursue these)
**Suspect A — the new inference engine's temporal/recurrent-state handling (LEADING).** The recovery-lag is a *same-model* comparison (Nevada on old engine 2.18 s vs new engine 3–6 s), so it isolates the difference to the **engine** (`sunnypilot/modeld_v2/`), not the Nevada model. A laggy/mis-fed recurrent state (features_buffer roll, subsampling, temporal-idx map, buffer length / is_20hz, cold-start/reset) would explain both slow perception recovery AND the delayed/weak offset correction (the model's path is slow to respond to a growing offset). **How to pursue:** diff `sunnypilot/modeld_v2/modeld.py` (ModelState temporal buffers) + `fill_model_msg.py` against the OLD modeld (`git show <old-commit>:selfdrive/modeld/modeld.py`; old commit `5e0785b98756`, or the fork's `selfdrive/modeld/`). Check features_buffer length, `temporal_idxs_map`, subsample stride, desire roll, and whether the recurrent state is fed/reset correctly. Cross-check against the sim's replication in `model_replay_sim/infer.py:265-423` (ReplayState.step) which documents the device math.

**Suspect B — the PI lane-centering state (concrete red flags).** `opendbc/car/ford/carcontroller.py` PI lane-centering (~lines 305-360) is **enabled** on device (`enable_lane_positioning=1`) and the code is byte-identical fork↔migration. BUT: (a) the persisted `LaneBiasIntegral = -0.3775` on device is **beyond the code's own ±0.30 cap** — stale/out-of-range; (b) the code carries an unresolved **`# SIGN VERIFICATION NEEDED`** comment (lines ~326-331) — the lane-offset correction sign was never confirmed against real logs; memory previously flagged this PI "reverse-causal." A wrong sign would push the car OFF-center; a stale integral biases steering. **How to pursue:** verify the sign from these drive logs (when the car is visually left of center, is `lane_offset` positive and the correction a right turn?), reset/validate the integral, and confirm whether the PI actually contributes correction during the §3.5 event (there `carOutput ≈ desiredCurvature`, i.e. the PI added ~nothing despite a 0.74 m offset — is it gated off, sign-cancelled, or under-gained?).
